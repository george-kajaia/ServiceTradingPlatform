# Security Review: Service Token Monetization Platform

**Date:** 2026-10-14
**Reviewer:** `security-reviewer` subagent (read-only). Key findings were spot-checked by the Engineering Manager session (see "Verification" at the end).
**Status:** Review only. No application code was changed.

**Scope:**
- `ServiceTokenAPI/ServiceTokenAPI`: all 9 controllers, `Services/Flitt`, `Services/Tbc`, `Hubs/RedemptionHub.cs`, `Program.cs`, the entities/DTOs these touch, and the tracked `appsettings.json` / `appsettings.Development.json` including their git history.
- How the four Angular UIs (`New/{AdminUI,CompanyUI,CustomerUI,ServiceUI}`) call the API: `core/api/*.service.ts`, login and state handling, `environments/*`.

**Method:** Every controller action and the payment, hub and startup code were read by hand, and every line number was checked against the file. Tracked files were listed with `git ls-files`, and all 7 commits that touch `appsettings*.json` were walked, checking only whether secret keys were present. **No secret values are reproduced here.** No files were modified. Nothing was run against a live environment.

## Summary

| Severity | Count |
|---|---|
| Critical (blocks release) | 7 |
| High | 5 |
| Medium | 6 |
| Low | 7 |

The API has no identity layer at all. Every endpoint is anonymous, and "who am I" is just a parameter the caller fills in. That alone makes most of the Criticals below exploitable with one HTTP request:
- Anyone can get tokens for free.
- Anyone can take another investor's tokens.
- Anyone can redirect a company's payouts to their own IBAN.
- Anyone can create admin accounts.
- Anyone can download every password in plaintext.

## Critical (blocks release)

### C-1: No authentication or authorization anywhere; identity comes from caller-supplied parameters
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Program.cs:98`: `UseAuthorization()` with no `AddAuthentication`.
  - No `[Authorize]` attribute exists in any controller.
  - `ServiceTokenAPI/ServiceTokenAPI/Hubs/RedemptionHub.cs:10`
- **Description:** Every action in all 9 controllers and the SignalR hub is anonymous. Actions take `investorPublicKey`, `companyId`, `investorId`, etc. from the query or body and trust them. The UIs' login screens only gate the UI. "Admin" actions are open to anyone who can reach `https://service-tokens.com/api`:
  - `Company/Approve`, `Investor/Approve`
  - `Request/Authorize`, `Request/Approve`
  - all `User/*`
  - domain CRUD
- **Exploit:** Any of C-2 to C-6 below. Swagger (`/swagger`) lists every endpoint for the attacker (L-1).
- **Fix:** Add JWT bearer auth (`AddAuthentication().AddJwtBearer`) with a global `AuthorizationPolicy` fallback that requires an authenticated user. Mark only login, register, the public market lists and the payment `Callback`/`Return` as `[AllowAnonymous]`. Add role claims (`PlatformAdmin`, `CompanyAdmin`, `CompanyStaff`, `Investor`) plus `companyId` / `investorPublicKey` claims. Take identity from `User.FindFirst(...)` and never from parameters. See remediation phase 3.

### C-2: Every plaintext password is downloadable without logging in
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/UserController.cs:15-40` (`GetAll`), `:42-49` (`GetById`): returns the `User` entity, including `Password`.
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/InvestorController.cs:15-40` (`GetAll`), `:42-49` (`GetById`), `:51-61` (`Login` returns the full `Investor` at `:60`).
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/CompanyController.cs:248-271` (`GetAllUsers`), `:273-280` (`GetUserByName`), `:224-234` (`AdminLogin`), `:236-246` (`Login`): all return the `CompanyUser` entity, including `Password`.
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/UserController.cs:91-114`: `Update` returns `Ok(c)`, which includes the password.
- **Description:** Passwords are stored in plaintext (H-5) and serialised straight to anonymous callers. The page size limit of 200 is easy to step through.
- **Exploit:**
  ```
  GET /api/User/GetAll?take=200                 -> every platform admin's username + password
  GET /api/Company/GetAllUsers?take=200&skip=0  -> every company admin/staff credential + companyId
  GET /api/Investor/GetAll?take=200             -> every investor username + password + PublicKey
  ```
  The attacker then logs into AdminUI, CompanyUI, ServiceUI or CustomerUI as anyone.
- **Fix:** Return response DTOs that have no `Password` field, from every action. Never return entities. Put the user-listing endpoints behind admin authorization. Hash passwords (H-5). Because these values have been exposed, treat every current password as compromised and force a reset.

### C-3: Anyone can take ownership of tokens without paying
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:396-442` (`BuyPrimaryServiceToken`)
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:444-486` (`BuySecondaryServiceToken`)
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:174-257` (`MarkServiceTokenInCart`)
- **Description:** These two endpoints move a token from `InCart` to `Sold` and assign `OwnerPublicKey` from a query parameter. They never check for a `Payment`. CustomerUI now pays through Flitt (`cart.component.ts:72-80` routes to `/checkout`). However, the old direct-buy path still exists:
  - The client methods are still in all three UIs: `New/CustomerUI/src/app/core/api/service-token-api.service.ts:42,60`, plus the same methods in AdminUI and CompanyUI.
  - The dead `processNext` path is still in `New/CustomerUI/src/app/features/investor/cart/cart.component.ts:82-113`.
  - The endpoints are live on the API.
- **Exploit:**
  ```
  GET  /api/ServiceToken/GetPrimaryMarketServiceTokens                -> id, rowVersion
  POST /api/ServiceToken/MarkServiceTokenInCart?serviceTokenId=<id>&rowVersion=<rv>&investorPublicKey=<mine>
  POST /api/ServiceToken/BuyPrimaryServiceToken?serviceTokenId=<id>&rowVersion=<rv+>&investorPublicKey=<mine>
  ```
  The token is now owned by the attacker and nothing was paid. Repeat for the whole primary market.
- **Fix:** Delete `BuyPrimaryServiceToken` and `BuySecondaryServiceToken`, or restrict them to `PlatformAdmin` for manual corrections. The only path to `Sold` should be `PaymentController.FinalizePrimaryPurchaseAsync` after a verified payment. Remove the matching UI service methods and the dead `processNext` code in CustomerUI, AdminUI and CompanyUI.

### C-4: Any caller can resell, and then take, another investor's token
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:488-519` (`MarkServiceTokenForResell`): no owner check.
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:521-559` (`CancelReselling`): no owner check.
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:22-68` (`GetInvestorServiceTokens`): returns any investor's token `Id` and `RowVersion` given their public key.
- **Description:** Investor public keys can be listed (C-2: `Investor/GetAll`). With a victim's key, an attacker gets the `Id` and `RowVersion` of every token the victim holds. They can flip each one to `Available` and then buy it, either for free (C-3) or at the original issue price via Flitt (H-4, where the victim receives nothing).
- **Exploit:**
  ```
  GET  /api/ServiceToken/GetInvestorServiceTokens?investorPublicKey=<victim>
  POST /api/ServiceToken/MarkServiceTokenForResell?serviceTokenId=<id>&rowVersion=<rv>
  POST /api/ServiceToken/MarkServiceTokenInCart?...&investorPublicKey=<attacker>
  POST /api/ServiceToken/BuySecondaryServiceToken?...&newInvestorPublicKey=<attacker>
  ```
- **Fix:** In every token mutation, require that `token.OwnerType == Investor` and `token.OwnerPublicKey` equals the caller's claim (resell, cancel resell, redeem-QR generation). `GetInvestorServiceTokens` should return only the caller's own tokens.

### C-5: Anyone can change any company's payout IBAN and divert settlement funds
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/CompanyController.cs:116-176` (`Update`; IBAN upsert at `:134-160`).
  - Funds are paid to that IBAN at `ServiceTokenAPI/ServiceTokenAPI/Controllers/PaymentController.cs:336-372`.
- **Description:** `Update` takes `companyId` and `rowVersion` from the query and a full `CompanyRequestDto`, and overwrites `BankAccount.Iban` and `BeneficiaryName`. `GetById` (`CompanyController.cs:47-57`) hands out the current `RowVersion`. Settlement later sends the company's share to whatever IBAN is stored.
- **Exploit:**
  ```
  GET /api/Company/GetById/7                          -> RowVersion + all fields
  PUT /api/Company/update?companyId=7&rowVersion=<rv>  body = same fields, BankAccountIban=<attacker IBAN>
  ```
  Every later card payment for company 7's tokens settles to the attacker.
- **Fix:** Require the `CompanyAdmin` role with a `companyId` claim equal to the route id. Treat IBAN changes as a sensitive action: re-enter the password, notify the company by email, and hold payouts or require platform-admin approval for N days after a change. Log every change to an audit table.

### C-6: Anyone can create or modify accounts, including platform admins and company admins
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/UserController.cs:63-89` (`create`), `:91-114` (`update`: sets any user's password), `:116-125` (`delete`).
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/CompanyController.cs:282-313` (`CreateUser`: `UserType` and `CompanyId` come from the body, `:296-297`), `:315-346` (`UpdateUser`), `:348-372` (`DeleteUser`).
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/InvestorController.cs:92-123` (`update`: sets `UserName` and password for any `investorId`), `:125-145` (`Approve`), `:147-167` (`delete`).
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/CompanyController.cs:178-198` (`Approve`), `:200-220` (`delete`).
- **Exploit:**
  ```
  POST /api/User/create                {"userName":"x","userFullName":"x","password":"p"}           -> AdminUI login
  POST /api/Company/CreateUser         {"userType":<Admin>,"companyId":7,"userName":"x","password":"p"}
                                                                                                  -> CompanyUI AdminLogin as company 7
  PUT  /api/Investor/update?investorId=3&rowVersion=<rv>  {"publicKey":"<same>","userName":"<same>","password":"p"}
                                                                                                  -> investor account takeover
  ```
- **Fix:**
  - `User/*`, `Company/Approve` and `Investor/Approve`: `PlatformAdmin` only.
  - `CreateUser`, `UpdateUser` and `DeleteUser`: `CompanyAdmin` of the same company. `CompanyId` comes from the claim, not the body.
  - Password changes need the current password, done in a dedicated endpoint.

### C-7: Secrets committed to git, including the database password
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/appsettings.json:3`: a value for `ConnectionStrings:ServiceTokens` is present. It contains a `Password=` for user `postgres` on an AWS RDS host. The password is in **all 7 commits** that touch this file, from `076c410` (2025-12-30) to `4b25e04` (2026-06-27).
  - `ServiceTokenAPI/ServiceTokenAPI/appsettings.json:22-23`: values for `Flitt:SecretKey` and `Flitt:PayoutSecretKey` are present, in commits `86a19d3`, `488555f` and `4b25e04`. They appear to be the provider's published sandbox credentials; see H-3 for why that matters.
  - Git history, commit `2a738da` (2026-06-04): a `Tbc` section had non-empty values for `ApiKey`, `ClientId`, `PurchaseSecretKey` and `PayoutSecretKey`. The `ApiKey` value is high-entropy and looks like a real credential. The section has since been removed from the working tree, but it stays in history.
  - `TestAPI/ServiceTokenAPI/appsettings.json` is also tracked. It is a clone of the same history, so the same exposure is in a second repo.
  - The project already has a `UserSecretsId` (`ServiceTokenAPI/ServiceTokenAPI/ServiceTokenAPI.csproj:7`), so the right tooling is in place but not used.
- **Exploit:** Anyone with read access to `github.com/george-kajaia/ServiceTokenAPI` (and `TestAPI`) gets full DBA access to the database (as user `postgres`) if the RDS endpoint can be reached from their network. That gives full read/write of tokens, payments and IBANs, bypassing every API control. Repo visibility and RDS security-group rules were **not verified**.
- **Fix:**
  1. Rotate the RDS `postgres` password now. Create a least-privilege app role and use it in the connection string.
  2. Rotate the TBC API key and secrets. Move Flitt to production credentials held only in env vars or AWS Secrets Manager.
  3. Replace values in `appsettings.json` with placeholders. Use `dotnet user-secrets` locally and environment variables on EC2.
  4. Rewriting history (`git filter-repo`) is optional once credentials are rotated. Rotation is what matters.
  5. Restrict the RDS security group to the EC2 instance.

## High

### H-1: Anyone can mint tokens; request approval has no state machine and can repeat
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/RequestController.cs:210-279` (`Approve`: no `Status == Authorised` check at `:218`; loop over `ServiceTokenCount` at `:228`).
  - `:164-185` (`Authorize`), `:187-208` (`Deauthorize`), `:120-140` (`Update`: allowed in any status), `:101-117` (`Create`: `CompanyId` and `ProductId` from the body; the product is not checked to belong to that company; `ServiceTokenCount` is not bounded).
- **Description:**
  - `Approve` can be called directly on a `Created` request.
  - It can be called again after approval using the new `RowVersion`, which issues a second batch of tokens.
  - A request can be edited after approval (`Update` raises `ServiceTokenCount`) and then approved again.
  - A company can file a request against another company's `ProductId`. The tokens then show B's product and price, but `CompanyId` = A, so settlement pays A.
  - A huge `ServiceTokenCount` (for example 50,000,000) loads millions of entities into memory, a DoS.
- **Exploit:**
  ```
  POST /api/Request/Approve?requestId=12&rowVersion=<rv>   -> N tokens
  GET  /api/Request/GetById/12                              -> new rv
  POST /api/Request/Approve?requestId=12&rowVersion=<rv2>  -> N more tokens
  ```
- **Fix:**
  - `Approve` only by `PlatformAdmin`, and only from `Authorised`. Make it idempotent: reject if `Status == Approved` or tokens already exist for `RequestId`.
  - `Update`, `Delete` and `Deauthorize` only while `Created` (or `Authorised`).
  - Validate `product.CompanyId == request.CompanyId == caller's companyId`.
  - Cap `ServiceTokenCount`, e.g. `[Range(1, 10000)]`.

### H-2: Anyone can redeem any token, regardless of company or expiry
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:567-638` (`GetService`).
  - The scanner trusts the QR payload: `New/ServiceUI/src/app/features/service/scan-token/scan-token.component.ts:83-98`.
  - QR contents: `New/CustomerUI/src/app/features/investor/get-service/get-service.component.ts:53-58`.
- **Description:**
  - `GetService` takes `serviceTokenId`, `rowVersion` and `connectionId` from the query. It does not check that the caller is staff of `token.CompanyId`, because there is no caller identity.
  - The QR's `companyId` is ignored by both ServiceUI and the API.
  - `EndDate` is never checked, so expired tokens can be redeemed.
  - The QR is not actually needed: `Id` and `RowVersion` are public via `GetInvestorServiceTokens` and `GetSecondaryMarketServiceTokens`.
- **Exploit:** A griefer burns every service use on a victim's token. Repeat this call, reading the new `rowVersion` each time:
  ```
  POST /api/ServiceToken/GetService?serviceTokenId=<id>&rowVersion=<rv>&connectionId=x
  ```
  Separately, staff at company A can "redeem" company B's tokens.
- **Fix:**
  - Require the `CompanyStaff` or `CompanyAdmin` role, and check `token.CompanyId == claim companyId`.
  - Check `EndDate >= today`.
  - Make the QR a short-lived, server-signed, one-time nonce instead of a raw token id. For example, issue `POST /api/ServiceToken/{id}/RedeemCode` to the owning investor with a 60-second expiry, stored hashed, and redeem by that code.
  - ServiceUI: send the code and drop the trust in client-side fields.

### H-3: The Flitt callback can be forged if production uses the committed sandbox key; callback amounts are not cross-checked
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/PaymentController.cs:118-145` (`Callback`), `:245-300` (`ApplyOutcomeAsync`).
  - `ServiceTokenAPI/ServiceTokenAPI/Services/Flitt/FlittModels.cs:188-198` (`Verify`).
  - `ServiceTokenAPI/ServiceTokenAPI/appsettings.json:21-23` (`MerchantId`, `SecretKey` and `PayoutSecretKey` are present).
- **Description:** The signature check itself is correct (SHA-1 over sorted params, Flitt's scheme). But the merchant id and keys in the tracked prod config appear to be Flitt's public sandbox credentials. If production does not override them with env vars (**unverified**), anyone can compute a valid signature. Even with a real key, `ApplyOutcomeAsync` never compares the callback's `amount`, `currency` or `merchant_id` with the stored `Payment` rows.
- **Exploit** (only if the sandbox key is live in production):
  1. `POST /api/Payment/InitiateEmbeddedPaymentBatch` and get `orderId`.
  2. `POST /api/Payment/Callback` with `{order_id, order_status:"approved", amount, ..., signature=sha1(<known key>|...)}`.
  3. The tokens are marked Sold and settlement is triggered.
- **Fix:**
  - Use production Flitt credentials from secrets only (C-7). Fail startup (`ValidateOnStart`) if `SecretKey` is a known test value in `Production`.
  - In `ApplyOutcomeAsync`, require `merchant_id == _options.MerchantId`, `amount == ToMinor(sum(payments.Amount))` and `currency` to match. If they don't, log and ignore.
  - Use `CryptographicOperations.FixedTimeEquals` for the comparison.

### H-4: Secondary-market sales paid via Flitt send the money to the issuing company; the reselling investor gets nothing
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/PaymentController.cs:519-554` (`FinalizePrimaryPurchaseAsync`: handles any `InCart` token, including investor-owned ones).
  - `:314-333`: shares are computed per `token.CompanyId`.
  - `:62`: the price charged is `token.Price`, the original issue price.
  - CustomerUI checkout sends both primary and secondary cart items: `New/CustomerUI/src/app/core/services/checkout-flow.service.ts:118-135`.
- **Description:** When investor B pays for investor A's resale token, ownership moves to B, the operation is logged as `BuyPrimary`, and settlement pays the issuing company (minus fee). Investor A loses the token and gets no money. Combined with C-4, this lets an attacker pay at issue price to take any investor's token.
- **Fix:** Until seller payouts exist, block investor-owned tokens in `InitiateEmbeddedPaymentBatch` (`token.OwnerType != Company` → 400). Then implement secondary settlement to the seller's IBAN with a seller-set price stored on the listing.

### H-5: Plaintext password storage and comparison across all account types, with no brute-force protection
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/UserController.cs:54, 69, 102`
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/InvestorController.cs:54, 70, 106`
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/CompanyController.cs:66, 227, 239, 292, 299, 325, 332` (`CreateUser`/`UpdateUser` also ignore the local `hash` variable)
  - `ServiceTokenAPI/ServiceTokenAPI/Configurations/CompanyUserConfiguration.cs:13`: a database index on `(UserName, Password)`.
  - No `AddRateLimiter` anywhere.
- **Description:** BCrypt is commented out everywhere. Logins compare plaintext in SQL. Logins return 404 vs 200, so usernames can be enumerated, and there is no rate limiting or lockout.
- **Exploit:** Online password guessing against `/api/Investor/Login`, `/api/Company/AdminLogin` and `/api/User/Login`. Any database read (C-7) or API dump (C-2) exposes every credential directly.
- **Fix:**
  - Use `Microsoft.AspNetCore.Identity.PasswordHasher<T>` (no new package needed) or BCrypt.Net-Next with work factor 12.
  - Look up the user by `UserName`, then `VerifyHashedPassword`.
  - Migration path: add a `PasswordHash` column, hash existing values on deploy (or on next successful login), then drop `Password` and the `(UserName, Password)` index in a later migration.
  - Add `builder.Services.AddRateLimiter` with a fixed-window policy per IP and username on the login actions.
  - Return a uniform 401 on failure.

## Medium

### M-1: Payments can be captured without delivering a token, and there is no automatic refund
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/PaymentController.cs:48-63`: no check of `Status == InCart`, or that the cart entry belongs to `request.InvestorPublicKey`.
  - `:519-527`: the paid token is "no longer in cart" → `Failed`.
  - `:268-274`: no reversal call.
- **Description:** Two buyers, or one buyer with two tabs, can create orders for the same token. The token can also be `Sold` or `Finished` already. When both payments are approved, the second is marked `Failed` but the card has been charged and nothing reverses it. `FinalizePrimaryPurchaseAsync` also gives the token to the payer even if it is in someone else's cart.
- **Fix:**
  - At initiate, require `Status == InCart`, a `ServiceTokenInCart.OwnerPublicKey` equal to the caller, and no other non-final `Payment` for the token.
  - On a finalization failure after approval, call Flitt reverse/refund and record it.

### M-2: Cart squatting, and cancelling other investors' carts
- **Location:** `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:174-257` (`MarkServiceTokenInCart`), `:259-339` (`CancelInCart`).
- **Description:** There is no owner check and no reservation expiry. A script can put every `Available` token `InCart` for a throwaway key and keep it there forever, shutting down the primary and secondary markets. Anyone can also cancel any other investor's cart reservation.
- **Fix:** Bind cart operations to the caller's claim. Add `ReservedUntil` (e.g. 15 minutes) with a background sweep or a check at read time. Cap concurrent reservations per investor.

### M-3: Product mass assignment and cross-company product edits; unvalidated pictogram upload
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ProductController.cs:48-54`: `Create` binds the whole `Product` entity, so the client sets `Id`, `CompanyId` and the nested `ProductPictogram`.
  - `:56-70` (`Update`, including `Price`), `:72-81` (`Delete`), `:85-110` / `:112-127` (pictogram add/replace): any product.
  - Pictogram upload has no size or type check (Kestrel's default 30 MB limit applies). Bytes are always served as `image/png` (`:137`).
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/EconomicActivityDomainController.cs:23` and `LegalFormDomainController.cs:23` bind entities, so the client can set `Id`. Low impact.
- **Exploit:** Company A runs `PUT /api/Product/Update?ProductId=<B's>` with `Price=0.01`. Future token batches for B are issued at that price. A can also replace B's pictogram with offensive content shown on the public market.
- **Fix:**
  - Use a `ProductRequestDto` and set `CompanyId` from the claim.
  - Check ownership on update and delete.
  - Pictogram: `[RequestSizeLimit(512_000)]`, check PNG/JPEG magic bytes, store the real content type, and add `X-Content-Type-Options: nosniff`.

### M-4: PII and payment-method data exposed, and deletable by anyone
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/CompanyController.cs:47-57` (`GetById`: returns IBAN and beneficiary).
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/InvestorController.cs:172-190` (`GetPaymentMethod`: masked card, brand, IBAN of any investor id), `:192-201` (`DeletePaymentMethod`: any investor).
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/CompanyController.cs:21-45` (`GetAll`: company mail and phone).
- **Exploit:** Iterate `GET /api/Investor/GetPaymentMethod/{1..N}` to collect investor IBANs and masked cards.
- **Fix:** Owner-only access, enforced by claims. Use separate public DTOs for company listings without contact or bank fields.

### M-5: Unbounded list responses with inline images (amplification DoS)
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:22-68, 70-118, 120-171, 341-393`: no `skip`/`take`, and every row includes the full `Pictogram` byte array.
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/RequestController.cs:25-60` (`GetAll`): no limit.
- **Description:** After H-1 minting, or simply with organic growth, one anonymous `GET /api/ServiceToken/GetPrimaryMarketServiceTokens` can return thousands of rows, each with an image of up to 30 MB (M-3). That exhausts memory and bandwidth.
- **Fix:** Paginate with a clamp (the same pattern as `Company/GetAll`). Return a pictogram URL (`/api/Product/{id}/Pictogram`, cacheable) instead of bytes.

### M-6: Passwords echoed in responses and stored in browser session storage
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/CompanyController.cs:113` (`Ok(Company)`: echoes the DTO including `Password`).
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/InvestorController.cs:89` (`Ok(investor)`).
  - `New/CustomerUI/src/app/core/state/investor-state.service.ts:25`: stores the full `Investor` from `Login` in `sessionStorage`. The model has a `password` field (`New/CustomerUI/src/app/shared/models/user.model.ts:7,14`); set at `investor-login.component.ts:54`.
- **Description:** Any XSS, a malicious browser extension, or a shared machine exposes the investor's plaintext password. Lower impact than C-2, but it outlives the API fix unless the UI model changes too.
- **Fix:** Response DTOs without passwords. In the UI, remove `password` from the stored model. After phase 3, store only the access token, in memory or as an HttpOnly cookie.

## Low

### L-1: Swagger UI is always on in production
- **Location:** `ServiceTokenAPI/ServiceTokenAPI/Program.cs:84-88`.
- **Description:** With no auth, it is a ready-made attack console.
- **Fix:** Wrap it in `if (app.Environment.IsDevelopment())`, or protect it with the admin policy.

### L-2: CORS allows localhost origins with credentials in the production config
- **Location:** `ServiceTokenAPI/ServiceTokenAPI/appsettings.json:38-43`, `ServiceTokenAPI/ServiceTokenAPI/Program.cs:26-30`.
- **Description:** Today no cookies are used, so impact is minimal. If cookie auth is added, any page served from a user's `localhost:420x` (e.g. a malicious dev tool) could make credentialed calls.
- **Fix:** Move the localhost origins to `appsettings.Development.json` only.

### L-3: Forwarded headers are trusted from any source
- **Location:** `ServiceTokenAPI/ServiceTokenAPI/Program.cs:40-41`.
- **Description:** If Kestrel is reachable without going through Nginx (**unverified**), clients can spoof `X-Forwarded-For` and `X-Forwarded-Proto`. That would defeat IP-based rate limiting (H-5 fix) and pollute logs.
- **Fix:** Add `KnownProxies.Add(IPAddress.Loopback)` (or the Nginx IP) and bind Kestrel to `127.0.0.1`.

### L-4: Provider error detail returned to clients and IBANs written to logs
- **Location:**
  - `ServiceTokenAPI/ServiceTokenAPI/Controllers/PaymentController.cs:108`: returns `ex.Message`, which includes up to 300 characters of the raw Flitt body (`FlittPaymentService.cs:67`).
  - `PaymentController.cs:426-427`: logs the raw settlement body.
  - Settlement payloads contain IBANs.
- **Fix:** Return a generic message with a correlation id. Remove IBANs from logged bodies.

### L-5: Order-status reconciliation accepts responses with invalid signatures
- **Location:** `ServiceTokenAPI/ServiceTokenAPI/Controllers/PaymentController.cs:189`.
- **Description:** The check is `order.SignatureValid || order.OrderStatus is not null`. The source is Flitt over TLS, so this is defence-in-depth only.
- **Fix:** Require `SignatureValid`.

### L-6: Unauthenticated SignalR hub, and the server pushes to any supplied connection id
- **Location:** `ServiceTokenAPI/ServiceTokenAPI/Hubs/RedemptionHub.cs:10-14`; `ServiceTokenAPI/ServiceTokenAPI/Controllers/ServiceTokenController.cs:579, 589, 621, 629`.

  - `ServiceTokenAPI/ServiceTokenAPI/Entities/InvestorPaymentMethod.cs:222`: the Flitt `rectoken` is stored unencrypted. No endpoint charges it today.

## Positive observations

- Prices and payment totals are computed on the server from `ServiceToken.Price`. The client only sends token ids (`PaymentController.cs:52-65`).
- The Flitt callback checks a signature before doing anything and acknowledges silently on failure (`PaymentController.cs:125-130`). Status changes are idempotent: final payments are skipped (`:250-256`) and settlement is guarded by `SettledAt` (`:305`).
- `RowVersion` is mapped as a PostgreSQL `xmin` concurrency token on tokens, requests, companies, investors and payments. Concurrent buy/redeem races end in `DbUpdateConcurrencyException`, so double redemption of one state is blocked, and an exact QR replay fails after the first redemption.
- No raw SQL. All queries are EF LINQ; `ILike` patterns are parameterised.
- The full card number is never stored. Only the masked card and a provider token.
- `Payment/Return` builds its redirect from config plus an encoded query value, so it is not an open redirect.
- Page sizes are clamped on `Company`, `Investor`, `User` and `Product` `GetAll`.
- No UI uses `localStorage` for identity, and there are no `bypassSecurityTrust*` sinks.

## Proposed remediation order

1. **Contain (same day, API only).**
   - Rotate the RDS `postgres` password, the TBC key set and the Flitt credentials. Move all of them to env vars or Secrets Manager and put placeholders in `appsettings.json` (both `ServiceTokenAPI` and `TestAPI`).
   - Restrict the RDS security group.
   - Turn off Swagger in production.
   - Temporarily block the most dangerous anonymous endpoints at Nginx until phase 3 ships:
     - `User/*` except `Login`
     - `Company/GetAllUsers`, `Company/GetUserByName`, `Company/CreateUser`, `Company/UpdateUser`
     - `Investor/GetAll`
     - `ServiceToken/BuyPrimaryServiceToken`, `ServiceToken/BuySecondaryServiceToken`
     - `Request/Approve`
     - `Company/update`
   - **UI impact:** check that the AdminUI user screens and CompanyUI user management are not needed during the freeze.
2. **Stop leaking passwords (API, then UIs).** Introduce response DTOs without `Password` for every User, Investor and CompanyUser response, and force a password reset for everyone. **UI impact:** update `shared/models/user.model.ts` in all four UIs, and stop persisting `password` in CustomerUI `investor-state.service.ts`.
3. **JWT auth + `[Authorize]` + identity from claims.**
   - Login returns a JWT with role and `companyId`/`investorPublicKey` claims. Use a fallback policy that requires authentication.
   - Remove `investorPublicKey`, `companyId` and `investorId` parameters from actions, or verify them against the claims.
   - Add owner checks for C-4, C-5, M-2, M-3 and M-4, and role checks for C-6 and H-1. Secure the hub with `accessTokenFactory`.
   - **UI impact (all four, one coordinated release, via the `api-contract-sync` skill):** an `HttpInterceptor` adding `Authorization: Bearer`; route guards; removal of the identity parameters from every `core/api/*.service.ts`; SignalR `accessTokenFactory` in CustomerUI `signalr.service.ts`.
4. **Password hashing with migration.** Add a `PasswordHash` column using `PasswordHasher<T>`, upgrade on login or with a one-off migration, drop the plaintext column and the `(UserName, Password)` index in a later migration. Add login rate limiting. No contract change except uniform 401s; check each UI's login error handling.
5. **Payment hardening.**
   - Delete the direct buy endpoints (C-3).
   - Cross-check `amount`, `currency` and `merchant_id` on callbacks; constant-time comparison; require `SignatureValid` (H-3, L-5).
   - Validate the cart owner and status at initiate, and reverse on finalization failure (M-1).
   - Block secondary-market items from checkout until seller settlement exists (H-4).
   - **UI impact:** remove `buyPrimaryServiceToken`/`buySecondaryServiceToken` from the CustomerUI, AdminUI and CompanyUI services and the dead cart code; CustomerUI checkout must handle a "secondary not purchasable" error.
6. **Token lifecycle.**
   - State machine for `Request` (H-1).
   - Redemption bound to company, expiry checked, short-lived signed one-time redeem codes (H-2).
   - Cart reservation expiry (M-2).
   - **UI impact:** the CustomerUI get-service QR payload changes; the ServiceUI scanner sends a code instead of `tokenId`/`rowVersion`.
7. **Hygiene.** Pagination and pictogram URLs (M-5; **UI impact:** every token list in CustomerUI, CompanyUI and AdminUI), upload validation (M-3), CORS cleanup, forwarded-headers proxy list, error-message and log redaction (L-2 to L-4).

Phases 2–6 each cross the API↔UI contract and count as "significant changes" under `.claude/rules/workflow.md`: each needs an approved plan saved to `docs/decisions/`.
